# 操作序列

四个场景的完整步骤，按顺序执行，每步都有检查点。

---

## A. 新建文档

**触发**：用户要一份新文档，或你判断该产出文档。

1. **定主题**：从用户描述里取名词短语，去掉「帮我写」「一份」这类词。
2. **定文件名**：`<主题>V1.0.md`，检查目录里是否已有同名文件。
3. **建变更表**：标题之后插入表头 + 一行 `V1.0 / 今天 / AI / 初版 / 创建文档…`。
4. **写正文**。
5. **自检**：
   - [ ] 文件名是 `主题V1.0.md`
   - [ ] 变更表在标题之后、正文之前
   - [ ] 表里版本号与文件名一致
   - [ ] 正文没有再写一遍版本号

**产出**：`用户中心设计V1.0.md`

---

## B. 更新文档（最常用）

**触发**：用户要改已有文档。

### B1 定位

```bash
ls 用户中心设计V*.md
```

- 只有一个 → 用它。
- 多个 → 取版本号最大者（见 `naming.md` 第五节），其余记下来，最后提示归档。
- 没有带版本号的同名文件，但有 `用户中心设计.md` → 走场景 C（纳入管理）。

### B2 读全

读**完整文件** + 变更表，记录：

- 上一版号（表里最新一行）
- 上一版日期与内容（用于判断这次改动的性质）
- 正文结构（哪些章节会受影响）

**检查点**：如果表里最新版本与文件名不一致，先停下来核对——说明上次改名或记表漏了一步。

### B3 改内容

- 只改需要改的部分，不顺手重排、不整文件重写。
- 新增章节插在合适位置，编号顺延。

### B4 记变更

**先读 `naming.md` 第二、三节再算**，按分支计算，不要做 `1.9 + 0.1` 这类小数心算：

```
minor < 9   →  V<major>.<minor+1>
minor = 9   →  V<major+1>.0
minor ≥ 10  →  文件名已非法，先按 `naming.md` 第四节规范化，不要继续升版
```

**检查点**：算出的次版本必须是 `0~9` 的单个数字。看到 `V1.10` / `V1.11` 就是算错，停下重算，不许带着错版本往下走。

在表格**第一行**插入：

```markdown
| V1.4 | 2026-11-13 | AI | 修订 | 一句话说明改了什么、为什么 |
```

### B5 改名

```bash
git mv 用户中心设计V1.3.md 用户中心设计V1.4.md
# 未被 git 跟踪时：mv 用户中心设计V1.3.md 用户中心设计V1.4.md
```

**顺序不能反**：先记表再改名。反过来会在「旧文件名 + 新版本号」的中间态里出错。

### B6 查引用

```bash
grep -rn "用户中心设计V1.3" --include="*.md" .
```

命中项逐个更新：目录页的链接、README 里的清单、其他文档的交叉引用。

**检查点**：

- [ ] 旧文件名在仓库里已无残留（除 git 历史）
- [ ] 变更表第一行的版本号 = 新文件名的版本号
- [ ] 新文件能正常打开，表格未错位

---

## C. 把无版本号文档纳入管理

**触发**：目标文件叫 `设计文档.md`、`方案.md`，没有版本段。

1. 读全文，判断当前内容算第几版——判断不了就按 `V1.0`。
2. 在标题后插入变更表，首行：`V1.0 / 今天 / AI / 初版 / 纳入版本管理，正文未改动`。
3. `git mv 设计文档.md 设计文档V1.0.md`
4. 查引用并更新。
5. 交付时明确说明：**这是改名，不是改内容**。

**注意**：纳入管理属于「修改文件名」，要更新所有引用；如果仓库里有外部系统按旧文件名拉取（脚本、流水线），先告知风险再动。

---

## D. 目标版本已存在（冲突）

**触发**：要改成 `V1.4`，但 `V1.4` 已经存在——通常是上次改到一半、或两人同时改。

处理顺序：

1. **不覆盖**。先把两个文件都列出来：`ls -l 用户中心设计V1.3.md 用户中心设计V1.4.md`。
2. 比对内容差异（`diff` 或直接读），判断哪个更新。
3. 分情况：
   - V1.4 是旧的一次改动且已合并 → 以 V1.4 为基准，升到 V1.5。
   - V1.4 是误建的空壳 → 报告用户，确认后删除空壳再升版。
   - 内容冲突无法判断 → **停下来问用户**，不要自行合并。
4. 在变更表里如实记录这次冲突的处理方式。

---

## E. 一次改多个文档

- 每个文档**独立**升版、独立记录、独立改名。
- 不要给一批文档共用一个版本号。
- 交付说明按文档分组列出：`A: V1.2→V1.3`、`B: V1.0→V1.1`。

---

## F. 用户要求不改名

用户说「名字别动」「文件名要固定，别人在引用」：

1. 内容照改，变更表照记（版本号按 `naming.md` 第二、三节继续升一版，次版本仍是 0~9）。
2. 文件名不动。
3. 交付说明里写明：`按用户要求未改名，文件名仍为 用户中心设计V1.2.md，变更表已记至 V1.3`。
4. 提醒一次风险：文件名与变更表版本不一致，后续接手的人容易误判。只提醒一次，不反复劝。

---

## G. 收尾：提交建议

改完后可以给一条提交命令（是否执行由用户决定）：

```bash
git add -A && git commit -m "docs: 用户中心设计 V1.3→V1.4，补充灰度发布章节"
```

提交信息里带上版本跨度，历史一眼能看懂。

---

## H. 人工改动补记

**触发**：文件被人手工改过，没升版、没记表。skill 管不到编辑器里的操作，只能在下次被调用时发现。

### 怎么发现

| 信号 | 判断方法 |
|---|---|
| 版本不一致 | 文件名 `V1.4`，变更表最新一行是 `V1.3` |
| 有改动无记录 | `git diff --stat` 里该文件有改动，但变更表没有新行 |
| 时间线可疑 | 文件 mtime 远晚于变更表最后一行的日期（仅供参考，拷贝会改 mtime） |

前两条任一命中即可确认；第三条只能当线索。

### 怎么处理

1. **先读改动内容**：`git diff 文件名` 看改了什么；没有 git 就只能看当前内容，判断不了就问用户。
2. **补一行**，版本号取当前文件名里的版本：

   ```markdown
   | V1.4 | 2026-11-13 | 张三 | 修订 | 补记：人工修改，调整容量评估的实例数，未同步升版 |
   ```

3. **变更人**写实际改动人；不知道写 `人工`。
4. **然后再做本次任务**：按正常流程升到 V1.5 并记新行。
5. **交付说明里说明**：`补记了 V1.4（人工改动），本次改动升至 V1.5`。

### 不要做的事

- 不要因为「人工已经改过」就跳过本次升版——两次改动各自占一个版本号。
- 不要把人工改动合并进本次新增行——混在一起，以后查不到是谁改的。
- 不要修改人工改动的内容——除非用户要求，否则只补记录。

---

## 检查清单（每次交付前）

- [ ] 文件名版本号 = 变更表最新一行
- [ ] **新版本号的次版本是 0~9 的单个数字**（不是 `V1.10` / `V1.11` / `V2.10`）
- [ ] 变更表新增行：日期、变更人、类型、一句话说明齐全
- [ ] 旧文件名引用已全部更新
- [ ] 没有产生多余的副本文件
- [ ] 正文里没有重复的版本号
- [ ] 如果有人工改动未记录，已补记（版本号、变更人、内容齐全）
- [ ] 交付说明写清了「旧名 → 新名」和「改了什么」
