# 变更记录表规范

## 一、位置

紧接文档标题之后，正文之前。如果文档有目录，放在**目录之前**——读者第一屏要看到的是「最近改了什么」，不是条目索引。

```markdown
# 用户中心设计

| 版本 | 日期 | 变更人 | 类型 | 变更内容 |
|---|---|---|---|---|
| V1.3 | 2026-11-13 | AI | 修订 | ... |

## 一、背景
...
```

不需要额外加 `## 变更记录` 标题，表格本身已经说明了。若文档结构要求必须有标题，用 `## 变更记录`。

## 二、列定义

| 列 | 取值规则 |
|---|---|
| 版本 | `V主.次`，与文件名严格一致 |
| 日期 | `YYYY-MM-DD`，改动的当天，不写「今天」 |
| 变更人 | `AI`（Agent 改动）/ 用户名（用户本人改）/ `人工`（不知道具体是谁的手工改动）/ `AI + 张三`（按用户要求共同署名） |
| 类型 | 只取四类：`初版` / `新增` / `修订` / `纠错` |
| 变更内容 | 一句话：改了什么 + 为什么。不超过 60 字，超了就分点写在正文里 |

**顺序**：最新在最上面（倒序）。新行永远插在表头下第一行。

## 三、类型怎么选

| 类型 | 用在 |
|---|---|
| 初版 | 文档第一次创建 |
| 新增 | 增加章节、段落、图、表，原有内容不动 |
| 修订 | 修改已有结论、方案、参数、结构 |
| 纠错 | 改错别字、错误数据、画错的图、失效链接 |

拿不准就用「修订」——它最中性。

## 四、写法对照

| ❌ 不合格 | ✅ 合格 | 差在哪 |
|---|---|---|
| 更新内容 | 登录态过期改为滑动窗口，按 11-12 评审意见调整时序图第 3 步 | 没说什么改了、为什么 |
| 优化了一下 | 把 3 个重复的审批分支合并为策略表，减少 40 行伪代码 | 没有可验证的信息 |
| 修改文档 | 补充灰度发布章节（4.2），新增回滚决策树 | 指不出位置 |
| 增加内容 | 新增「容量评估」一节，按 3 万 QPS 给出实例数与队列容量 | 没有量化 |
| fix bug | 修正权限模型中角色继承画反的问题 | 中英混用，看不出改了什么 |

判断标准：**三个月后回来看这一行，能不能知道当时改了什么。**

## 五、与正文的关系

- 正文**不重复版本号**。不要在页首写「版本：V1.3」、页脚写「最后更新于」——这些信息只活在文件名和变更表里。
- 正文里可以引用变更记录（「详见变更记录 V1.2」），但不要复制内容。
- 大段删减时，变更内容写「删除第 5 节旧方案」，不要留下大段注释掉的正文。

## 六、与 git 的分工

| | 变更记录表 | git |
|---|---|---|
| 读者 | 人（评审、交接、复盘） | 机器（回溯、比对） |
| 内容 | 为什么改、改了什么 | 逐行差异 |
| 粒度 | 一次编辑一行 | 一次提交 |

两者不冲突：表格是摘要，git 是底稿。所以**不要在文档里维护完整的历史正文**——那是 git 的活。

## 七、首次落表的完整片段

可直接复制：

```markdown
# 订单服务重构方案

| 版本 | 日期 | 变更人 | 类型 | 变更内容 |
|---|---|---|---|---|
| V1.0 | 2026-11-13 | AI | 初版 | 创建文档，含现状分析与拆分方案 |
```

第二次编辑后：

```markdown
# 订单服务重构方案

| 版本 | 日期 | 变更人 | 类型 | 变更内容 |
|---|---|---|---|---|
| V1.1 | 2026-11-14 | AI | 修订 | 拆分粒度由 3 个服务调整为 2 个，按 11-13 评审意见合并库存与计价 |
| V1.0 | 2026-11-13 | AI | 初版 | 创建文档，含现状分析与拆分方案 |
```

## 八、常见错误

1. **表头写错列序**——固定为 版本 / 日期 / 变更人 / 类型 / 变更内容，不要自创列。
2. **漏了某一次改动**——每次编辑必须落一行，包括「只改了个错别字」。
3. **版本号与文件名不一致**——文件名是 V1.3，表里最新写 V1.2，说明改名或记表漏了一步。
4. **把变更表放在文末**——读者翻到底才知道改了什么，失去意义。
5. **一天改多次却只记一行**——每次升版各记一行，日期可以相同。
