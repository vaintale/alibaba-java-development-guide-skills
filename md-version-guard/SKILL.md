# 文档版本守卫

> 项目文档最常见的两种失序：**不知道哪一版是最新的**，以及**不知道这次改了什么**。
> 这个 skill 用两条硬规则解决：版本号写进文件名，变更记录写进文档第一屏。

## 何时启用

| 场景 | 启用 |
|---|---|
| 新建项目文档（设计、方案、需求、复盘、报告） | ✅ 直接命名 `xxxV1.0.md` |
| 更新已有文档（补章节、改结论、按评审意见修改） | ✅ 升版 + 改名 + 记变更 |
| 把无版本号的历史文档纳入管理 | ✅ 规范化为 V1.0 并注明 |
| 改 README、CHANGELOG、LICENSE、CONTRIBUTING | 🔸 不改名（会破坏仓库约定与 GitHub 展示），内容变更照常 |
| 临时笔记、草稿、一次性输出 | 🔸 不启用；用户明确要留存时再纳入 |
| 改代码、改配置、改 SQL | ❌ 走 `java-edit-guard`，与本 skill 无关 |

## 一、两条硬规则

### 规则 1：版本号写在文件名里

```
主题V<主版本>.<次版本>.md      ← 例：用户中心设计V1.3.md
```

- 大写 `V`，紧贴主题，`V` 与数字之间**不留空格**。
- 初始版本 `V1.0`；**每次编辑 +0.1**：`1.1 → 1.2 → … → 1.9 → 2.0`（次版本满 9 进位，不存在 `V1.10`）。
- 主题部分不写日期、不写「最终版 / 最新版 / 修订版」——版本号已经表达了这件事。
- 文件名里只允许一个小数点版本段，`V1.0.1`、`V1.0-final` 都算非法。

### 规则 2：变更记录写在文档第一屏

紧接标题之后，正文之前：

```markdown
# 用户中心设计

| 版本 | 日期 | 变更人 | 类型 | 变更内容 |
|---|---|---|---|---|
| V1.3 | 2026-11-13 | AI | 修订 | 登录态过期改为滑动窗口，按 11-12 评审意见调整时序图第 3 步 |
| V1.2 | 2026-11-12 | AI | 新增 | 补充灰度发布与回滚章节 |
| V1.1 | 2026-11-12 | AI | 纠错 | 权限模型中的角色继承关系画错，已重画 |
| V1.0 | 2026-11-11 | AI | 初版 | 创建文档 |
```

- **最新在最上面**（倒序），打开文档第一眼看到最近一次改了什么。
- 类型只取四类：`初版` / `新增` / `修订` / `纠错`（删减内容也算修订，在说明里写清）。
- 变更内容一句话，写**改了什么 + 为什么**。「优化了一下」「调整部分内容」等于没写。
- 正文里**不再重复写版本号**（如页首「版本：V1.3」），避免与文件名、变更表三处不一致。

## 二、更新已有文档：六步

```
1. 定位     找到目标文件；同目录若有多个版本并存，取版本号最高的那个
2. 读全     读完整文件 + 变更记录表，拿到「上一版号」和「已记录内容」
3. 改内容   只改需要改的部分，不顺手重排、不整文件重写
4. 记变更   在表格顶部插入一行：新版本号 = 旧 + 0.1、今天日期、变更人、类型、一句话说明
5. 改名     原地改名 V1.2 → V1.3（不留副本，旧内容靠变更表 + git 回溯）
6. 查引用   grep 全仓旧文件名，把链接、目录、README 里的引用一并更新
```

第 6 步不能省——改名后最常见的故障是别处链接变成死链：

```bash
grep -rn "用户中心设计V1.2" --include="*.md" .
```

## 三、新建文档

1. 由标题推导文件名：去空格、去标点，保留中文与英文单词（`用户中心 设计方案` → `用户中心设计方案V1.0.md`）。
2. 变更表只写一行：`V1.0 / 今天 / AI / 初版 / 创建文档`。
3. 正文按需组织，但**变更表必须在标题之后**。

## 四、把历史文档纳入管理

文件没有版本号（`设计文档.md`）：

1. 读全文，判断当前内容属于哪一版——无法判断就按 V1.0。
2. 加变更表，首行写 `V1.0 / 今天 / AI / 初版 / 纳入版本管理，内容未改动`。
3. 改名 `设计文档V1.0.md`，更新引用。
4. 在交付说明里告诉用户「原文件已改名，历史内容未改」。

## 五、异常与边界

| 情况 | 处理 |
|---|---|
| 用户明确说「别改名」 | 只记变更表，文件名不动；交付说明里标注「未按规范改名」 |
| **文档被人手工改过**，没升版也没记表 | 先补记再继续（见下） |
| 目标新版本号的文件已存在 | **不覆盖**，报告冲突：列出两个文件，让用户决定保留哪个 |
| 版本号写法不规范（`v1.0`、`V1`、`V1.10`、`V1.0.1`） | 规范化为合法值并在变更表注明「修正版本号格式」；`V1.10` 按 `V2.0` 处理 |
| 同目录存在 V1.2、V1.3 两个文件 | 以 V1.3 为准继续改；V1.2 可能是历史遗留，提示归档，**不自动删** |
| 文档被别的文件引用（目录页、README） | 改名后同步更新引用，交付说明里列出改了哪几处 |
| 一次编辑涉及多个文档 | 每个文档独立升版，各自记录；不要共用一个版本号 |
| 用户只要「看一眼 / 总结一下」 | 不改文件、不升版 |

### 人工改动怎么补记

这个 skill 管不到人在编辑器里的手改，但能在下次被调用时发现痕迹。两个信号：

1. **文件名与变更表不一致**——文件是 V1.4，表里最新还是 V1.3。
2. **git 显示该文件有未提交改动，但变更表没动**——`git diff --stat` 里有它，表里没新行。

发现任一信号，先补记再干活：

```markdown
| V1.4 | 2026-11-13 | 张三 | 修订 | 补记：人工修改，调整了容量评估的实例数，未同步升版 |
```

- 版本号取「文件名当前版本」；内容能看清就写改了什么，看不清就写「补记人工修改，具体改动待确认」。
- 变更人写实际改动人；不知道写 `人工`。
- 补记完再按正常流程做本次改动（会再 +0.1）。
- 如果只是格式化、改错别字，也照样补一行——漏记比记多更麻烦。

## 六、交付说明（三段）

```
版本     旧文件名 → 新文件名（V1.2 → V1.3）
变更     本次改了什么、为什么；变更表新增的那一行原文
引用     同步更新了哪些文件里的链接；有残留则列出
```

不写「已完成」这种没有信息量的收尾。

## 八、反模式

1. 改了内容不升版，文件名还是 V1.2
2. 升了版但变更表没加行，或只写「更新内容」
3. 每次编辑另存一个新文件，目录里堆 V1.0~V1.7 七个文件
4. 文件名写 `最新版`、`最终版`、`V1.0-final`
5. 改名后不查引用，文档链接全断
6. 正文里再写一遍版本号，与文件名对不上
7. 把 README 也按这个规则改名

## 九、验收标准

把改后的文档交给同事，他看文件名知道是第几版，打开第一屏知道每一版改了什么——做不到就还没交付完。
