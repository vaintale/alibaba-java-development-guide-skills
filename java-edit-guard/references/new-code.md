# 新增与从零：建设协议

> `SKILL.md` 的 §1~§4 讲的是「改」。这份文件讲「加」——在既有工程里新增业务代码，以及空目录从零起项目。
> 两条路径共用 `SKILL.md` §5 红线、§3.3 风格继承、§4.1 验证、§4.3 交付说明。

---

## 0. 先分清是哪种「新增」

| | B1 在既有工程里新增 | B2 空目录从零起项目 |
|---|---|---|
| 判断依据 | 有同层代码可读、有调用链可接 | 没有存量，一切自定 |
| 默认半径 | R4（新类要接进现有链路） | 不适用半径，按条款清单建 |
| 核心动作 | **对齐**：读样本、接线路、看不出是新加的 | **定型**：先定分层与契约，再写业务 |
| 失败方式 | 风格不一致、漏接线、分层错位 | 结构没定就写业务，后期整体返工 |

绝大多数任务是 B1。「新建一个文件」不等于「从零」。

---

## 1. B0：大特性开工前（新增量大时先做这步）

**触发条件**（满足任一）：预计新增 10 个文件以上；涉及建表或改表；新增对外接口；跨 3 个以上模块；带消息、定时任务、缓存或外部依赖。

**产出一页纸**，四块，不写长文档：

1. **范围与边界**：这次做什么、明确**不**做什么；涉及哪些模块；哪些老代码要改（那部分走路径 A 的协议）。边界写不清，后面必然反复。
2. **契约先行**（最重要）：对外接口（路径、入参、出参、错误码）、表结构与索引变更、DTO/VO 字段与序列化名、枚举值。**契约定稿后不再随手改**——大特性返工的主因就是边写边改契约。
3. **分批**：按「可独立验证」切，每批 3~8 个文件，结束时可编译、可跑用例、可演示。不要 40 个文件一次性交。
4. **验收口径**：每批怎么验（单测 / 接口调通 / 数据核对 / 页面走查），整体上线前的端到端场景。

**设计图**：跨 3 个以上模块、或存在状态流转时，补用例图 / 时序图 / 状态图（`07` 设计规约）；单模块的增删改查不画图，别为流程而流程。

**为什么先做这步**：新增代码的失败很少是「某一行写错」，多是「结构没定就开写」——表结构改三次、接口字段改五次、分层放错导致大面积搬迁。B0 花半天，省后面几天。

## 2. B1：在既有工程里新增业务代码

### 2.1 写之前：对齐侦察

不写代码先做四件事，产出记在心里（不用写给用户）：

1. **找样本**：同层 2~3 个类，`Read` 完整实现。看包路径、类名后缀、类注解、字段注入方式、方法命名。
2. **走链路**：挑一条同类业务，从 Controller 跟到 SQL，记下每一层做什么、不做什么。
3. **记六项约定**：

| 约定 | 要看什么 |
|---|---|
| 异常 | 抛 `BizException` 还是自定义？错误码从哪个枚举取？全局处理器怎么映射？ |
| 返回 | `Result<T>` 还是直接返回对象？成功码是什么？分页用哪个包装？ |
| 事务 | `@Transactional` 加在 Service 还是 Manager？`rollbackFor` 写没写？ |
| 日志 | `@Slf4j` 还是自研封装？关键节点打什么关键字？ |
| 持久化 | MyBatis-Plus 还是手写 XML？`resultMap` 有没有强制要求？逻辑删除字段怎么配？ |
| 校验 | `@Valid` + JSR303 还是手写 `Assert`？分组校验用不用？ |

4. **找接线点**：路由前缀、Bean 名冲突、`@MapperScan` 包范围、配置项 key、权限注解、网关白名单。

### 2.2 建设顺序（每一步都要能编译）

```
DTO / Query（含校验注解）
  → DO + Mapper（resultMap / 列映射）
    → Service 接口（先定对外契约）
      → ServiceImpl（事务、异常、日志）
        → Controller（路由、校验、组装 VO）
          → 单元测试（Service 层为主）
            → 接线自检（扫描、配置、权限）
```

先接口后实现的好处：契约在写实现前就固定，避免「实现里顺手改签名」。

### 2.3 六个高频坑

1. **Service 返回 DO**——上层拿到 `is_deleted`、`version`、内部成本价。出参一律转 VO（`06-(一)`）。
2. **Controller 写业务或加事务**——事务边界应在 Service；Controller 只做校验、调用、组装。
3. **事务加在私有方法或同类内部调用**——Spring 代理不生效，静默无事务。
4. **新 Mapper 没被扫到**——`@MapperScan` 包范围不包含新包，启动即报 `NoSuchBeanDefinition`。XML 还要检查 `mapper-locations`。
5. **新配置项只改了本地 yml**——配置中心、K8s ConfigMap、环境变量模板漏一处，上线读到默认值。
6. **VO 直接复用 DO**——序列化字段名与前端约定不一致，或把内部字段透出（`04-2` 脱敏）。

### 2.4 验收清单

- [ ] 分层职责正确，与同类链路一致（`06-(一)`）
- [ ] 入参校验到位，分页参数有上限（`04-4【强制】`）
- [ ] 权限校验包含数据归属，不只是「登录了」（`04-1【强制】`）
- [ ] 事务在 Service 的写方法上，`rollbackFor` 显式声明（`02-(二)5`）
- [ ] 异常走既有体系，错误码复用不新造（`02-(一)6`）
- [ ] 日志门面与关键字和周边一致，无敏感信息（`02-(三)1`、`04-2`）
- [ ] 新类已被框架扫描/注册（Mapper、Bean、路由）
- [ ] 有对应单元测试，覆盖正常、边界、异常三类（`03`）
- [ ] 把新代码丢进同类文件堆里，看不出哪一个是新加的

## 3. B2：空目录从零起项目

### 3.1 先定五件事，再写第一行业务代码

| 顺序 | 定什么 | 依据 |
|---|---|---|
| 1 | **分层与包结构**：Controller / Service / Manager / DAO 各放哪，DTO/VO/DO 怎么分 | `06-(一)` |
| 2 | **依赖与版本**：统一 GAV、禁止 SNAPSHOT、避免同一包多版本 | `06-(二)` |
| 3 | **数据模型**：主键类型、`id/create_time/update_time` 三字段、逻辑删除、索引 | `05-(一)`、`05-(二)` |
| 4 | **错误码与异常体系**：5 位错误码、来源分段、全局处理器 | `02-(一)` |
| 5 | **测试骨架**：目录、命名、AIR/BCDE 用例分类 | `03` |

顺序不能颠倒：先写业务再补分层，等于返工。

### 3.2 最小可运行验收

从零项目的「验证」不是「代码写完了」，而是下面五条全过：

```
1. mvn -q -o compile / gradle compileJava 通过
2. 应用能启动，无 Bean 冲突、无循环依赖
3. 一个健康检查或最小查询接口能返回 200
4. 一条端到端用例跑通（HTTP → Service → DB → 返回）
5. 日志输出格式、级别、traceId 符合预期
```

### 3.3 常见坑

- **表字段类型与 DO 不匹配**：`bigint` 对 `Integer`、`decimal` 对 `Double`（`01-(四)11【强制】`）。
- **没有统一返回包装**：每个接口一种结构，前端逐个适配。
- **依赖冲突**：两个二方库带同一个包的不同版本，运行时 `NoSuchMethodError`。
- **时间字段用 `datetime` 但代码用 `LocalDate`**：精度丢失或反序列化失败。
- **没配逻辑删除**：`delete` 变成物理删除（`05-(一)10【强制】`）。

## 4. 交付说明的差异

新增任务的四段报告，重点和改存量不同：

| 段落 | 改存量 | 新增 / 从零 |
|---|---|---|
| 改了什么 | 文件:行号 + 一句说明 | 新增文件清单 + 每个类负责什么 |
| 依据 | 契约与红线条文 | 结构类条文（`06-(一)`、`05-(一)`）+ 红线 |
| 验证 | 编译 + 相关测试 + diff | 编译 + 启动 + 端到端用例 |
| 没做/风险 | 未修的相邻问题 | **未接的线**：未注册的 Bean、未加的配置、未接的权限、未覆盖的分支 |

「未接的线」必须写清楚——新增代码最常见的故障不是逻辑错，而是没接上。
