# Java 编辑守卫（java-edit-guard）

> 让 Coding Agent 在既有 Java 工程里**改代码、加业务**时不闯祸：先读全、只改该改的、与既有约定对齐、交付时说清改了什么。
> 规约底本：《Java 开发手册（黄山版）》v1.7.1。

---

## 一、这个 Skill 解决什么问题

AI 写新代码的问题已经说得很多了；但在真实工程里，Agent 的活基本都在**别人写过的代码旁边**——加个参数、修个 bug、补一个 Service、加一个接口。这类任务翻车的方式和「从零起项目」完全不同：

| 翻车方式 | 具体表现 | 后果 |
|---|---|---|
| **没读懂就改** | 只看了 50 行就动手，不知道同类方法已有工具类，不知道有 3 个重载 | 重复实现、编译不过、改错分支 |
| **改多了** | 顺手重排 import、整文件格式化、把 `for` 改 `stream`、重命名无关变量 | diff 几百行，review 无法进行，合并必冲突 |
| **破坏契约** | 改了方法签名没同步调用方、改了枚举值、改了 `@JsonProperty`、`@Transactional` 被同类调用绕开 | 上线即报错，且往往在非核心链路炸核心功能 |
| **带进红线** | 沿用文件里的 `Executors.newFixedThreadPool`、把 `SimpleDateFormat` 提成 static、`catch` 掉异常继续跑 | 线上 OOM / 数据错乱 / 事务不回滚 |
| **假验证** | 没编译、没跑测试，报告写「已验证通过」 | 问题延后到提测甚至线上 |

这些问题都不是「不懂规约」，而是**缺少一套编辑纪律**。本 Skill 就是这套纪律。

## 二、核心设计

两类任务、两条路径，共用同一套红线和交付要求：

| | 路径 A：改存量 | 路径 B：新增业务代码 |
|---|---|---|
| 典型任务 | 改方法、修 bug、重构、改 SQL | 新 Controller / Service / Mapper / DTO / 接口 |
| 核心机制 | 编辑半径 + 契约不变 + 最小 diff | 契约对齐 + 按序建设 + 接线自检 |
| 失败方式 | 破坏调用方、diff 噪声 | 风格不一致、漏接线、分层错位 |
| 详细流程 | `SKILL.md` §1~§4 | `SKILL.md` §11 + `references/new-code.md` |

只有「空目录从零起项目」走第三套轻量流程：按结构条款清单建（分层 → 依赖 → 建表 → 错误码 → 测试骨架），验收标准是能编译、能启动、一条端到端用例跑通。

新增量大时（10 个文件以上、要建表、加对外接口、跨 3 个以上模块），路径 B 前面多一步 **B0 前置契约**：范围与边界、接口与表结构、分批计划、验收口径——契约定稿再动手。大特性返工的主因不是写错某一行，而是边写边改契约。

### 1. 编辑半径分级

改之前先给改动定级，半径决定侦察深度：

| 半径 | 范围 | 门禁 |
|---|---|---|
| R1 | 单条语句 | 读上下文 20 行 |
| R2 | 单个方法体 | 读整个方法 + 入参来源 |
| R3 | 方法签名 / 字段 | 读整个类 + grep 全部调用方 |
| R4 | 跨类跨层 | 走通调用链 + 找测试 + 出方案 |
| R5 | 公共契约 | 只报告不实施，先给兼容方案 |

### 2. 十条契约清单

方法签名、异常类型、返回语义、序列化字段、表名列名、Spring Bean 与配置 key、事务与锁边界、同步异步模型、枚举值、对外 HTTP 契约——这十项默认不动，改了必须在报告里列影响面。依据是 `01-(四)4【强制】`。

**在既有工程里新增业务代码时，这十项从「不变」转为「对齐」**：没有旧签名要保，但要沿用同层的命名、异常体系、返回包装、事务位置与日志门面。判断标准是——新代码的调用方不该需要知道它是新加的。

### 3. 18 条红线

线程池、`SimpleDateFormat`、`ThreadLocal`、事务回滚、空 catch、资源关闭、`finally return`、SQL 注入、越权、脱敏、物理删除、`BigDecimal`、包装类 `==`、`java.sql.Date`……每条都有反例/正例代码和原文编号。

被本次改动触碰到的范围内发现红线：**必须修**，且「其他保持不变」不构成豁免。

### 4. 条文可溯源，不臆造

Skill 里每一条强制要求都写得出原文编号。社区流传但与黄山版不符的说法，单独列了一节纠正：

| 常见说法 | 黄山版实际 |
|---|---|
| 集合方法禁止 `return null` | `02-(二)10【推荐】` 明确允许返回 null，只需注释说明 |
| 双重检查锁必须 `volatile` | `01-(七)16` 是【推荐】，不是【强制】 |
| `update`/`delete` 必须带 `where` | 手册无此原文，相近的是「订正先 select」「禁物理删除」 |

另有 Google Java Style Guide 作为补充（`SKILL.md` §13）：只取手册未覆盖且不冲突的项；冲突一律以阿里为准（4 空格缩进、120 字符行宽、注释与异常口径等）。团队约定（如日期时间统一 `java.time`、禁 `java.util.Date`）按来源标注，不冒充手册强制条文。

## 三、目录结构

```
java-edit-guard/
├── SKILL.md                        # 唯一协议：半径分级 / 改前侦察 / 改中约束 / 改后验证 / 红线表
├── memory.md                       # 个人编辑偏好
├── evals/                          # 10 个 skill-up 评测用例 + 评分脚本
├── references/
│   ├── redlines.md                 # 18 条红线的反例→正例代码对照
│   ├── playbooks.md                # 9 个编辑动作手册（改签名 / 改 SQL / 改并发 / 加事务…）
│   ├── new-code.md                 # 新增与从零：对齐侦察 / 建设顺序 / 接线自检 / 结构条款清单
│   ├── diff-review.md              # diff 噪声清单 + 改后自检 + 大改策略
│   ├── report-template.md          # 四段交付说明模板与示例
│   └── manual/                     # 手册条文原文（01~08）+ index.md（321 条速查）
└── project/
    ├── README.md
    ├── _template.md                # 项目编辑画像模板（验证命令 / 分层 / 既有约定）
    └── _example.md                 # 虚构示例；真实 <项目名>.md 本地保存，不入公开仓库
```

## 四、安装与跨机器同步

本 Skill 是**单层结构**：只有一个协议 `SKILL.md` + `references/`。命中 Java 编辑任务后，宿主按 skill 的 `description` 加载它；没有常驻路由层，也不往仓库或具体 Java 项目投放规则文件。

### 1. 安装到当前机器

**WorkBuddy**：把整个 `java-edit-guard/` 目录放到 `~/.workbuddy/skills/` 下。

**Claude Code**：

```bash
mkdir -p ~/.claude/skills
cp -r java-edit-guard ~/.claude/skills/
```

安装后在 Java 项目里直接说需求即可，触发与细则都由 `SKILL.md` 承担。

### 2. 跨机器同步

本 Skill 只在你自己的多台电脑上使用，不为同事/CI 分发。同步方式：

```bash
git clone <你的仓库地址>
cp -r java-edit-guard ~/.workbuddy/skills/
```

更新时重新同步 `java-edit-guard/` 即可，但**保留安装侧本地的 `project/*.md`**（如 `project/topology-server.md`）——这些是你的本机项目画像，不入库、也不跨机器共享；这是已知且接受的现状，Skill 在文件不存在时会跳过。

### 3. 验证是否生效

安装后改一个 Java 文件，观察三点：是否先读完整文件、是否 grep 调用方、是否给出四段交付说明。缺一即 skill 未被加载。

安装后在 Java 项目里直接说需求即可，例如：

- 「在 `OrderService` 里加一个取消订单的方法」
- 「照着现有的售后链路，加一个退款申请接口」
- 「这个扣库存的逻辑有并发问题吗」
- 「给 `sendMessage` 加个 tag 参数，其他别动」
- 「review 一下我这个 diff」

## 五、使用示例

改动前的判断链（Agent 内部执行）：

```
需求：给 sendMessage 加 tag 参数
  ↓
定级：改签名 → R3
  ↓
侦察：读整个 MessageService；grep sendMessage → 4 处调用（含 1 个测试）
  ↓
发现：类里有 Executors.newFixedThreadPool(10)  ← 红线 01-(七)4，被触碰范围内，必须修
  ↓
执行：加参数 → 同步 4 处调用 → 线程池改 ThreadPoolExecutor 显式参数
  ↓
验证：mvn -q -o compile + MessageServiceTest
  ↓
交付：四段说明（改了什么 / 依据 01-(七)4 / 验证结果 / 未跑的集成测试）
```

新增业务的判断链（路径 B）：

```
需求：照着售后链路，加一个退款申请接口
  ↓
分流：既有工程新增 → R4（§11 B1）
  ↓
对齐：读同层 2 个 Controller/Service；走通售后链路；记下异常、返回包装、事务位置、校验方式
  ↓
建设：DTO → Mapper → Service 接口 → Impl → Controller → 单测（每步可编译）
  ↓
接线：@MapperScan 包范围、路由前缀、权限注解、配置项
  ↓
交付：四段说明 +「未接的线」清单
```

## 六、个性化

两层配置，按优先级合并：

```
memory.md（个人习惯） → project/<项目名>.md（项目约定） → 手册基线
```

`project/<项目名>.md` 里最要紧的一节是**验证命令**——没有它，「改后验证」只能写「未验证」。首次在某项目编辑时，Agent 会扫描构建文件并询问后生成。

## 七、评测

`evals/` 下有 10 个 skill-up 格式用例，覆盖命名风格、NPE、SQL 注入、日期时间、工程分层、集合并发、坏代码审查、金额计算，以及两个存量场景：加功能时不许改坏、线程池红线必须强制修复。

用例不引用 skill 名，换目录可直接跑；`evals/eval.yaml` 的 `engine` 当前是 `claude_code`，换平台改这一处即可。评分脚本在 `evals/fixtures/scripts/`，按用例的 `judge` 规则打分。

用例改编自 [Sxuan-Coder/alibaba-java-development-guide](https://github.com/Sxuan-Coder/alibaba-java-development-guide)（MIT），原样收录并在 `evals/README.md` 标注来源。

## 八、边界

- 本 Skill 只管**改代码的过程**，不替代 code review、不替代 CI 静态检查（P3C / PMD）。
- 手册条文版权归阿里巴巴集团所有；封装部分（协议、模板、示例）可按 MIT 使用。
- 条文由 PDF 转换而来，可能有少量排版噪声，引用以语义为准。
